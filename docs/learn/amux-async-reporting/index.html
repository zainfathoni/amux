Lesson 1 · Amux async reporting

Mailbox, bukan CCTV

Cara coordinator tahu subagent sudah selesai tanpa terus membuka session yang masih berjalan.

Mas firewalker06, problemnya valid: kemampuan membaca session kapan saja bukan mekanisme completion. Itu seperti PM yang berkali-kali membuka layar engineer. Yang dibutuhkan adalah durable mailbox untuk hasil dan doorbell murah untuk membangunkan coordinator.

Jawaban pendek: iya, pola yang dibangun di amux memang menyelesaikan kelas masalah itu. Subagent menulis report lebih dulu, lalu callback hanya membangunkan agent. Tetapi untuk work Amp baru, kami sekarang memilih native parent/child reply routing; report/group Amux sedang menjadi jalur kompatibilitas untuk state lama. /amux-tycho tetap eksperimen khusus executor eksternal.

Kontrak intinya: simpan dulu, bunyikan bel kemudian

1 · SubagentSelesai atau blocked, lalu submit report terstruktur.
→
2 · Durable storeReport menjadi sumber kebenaran yang tahan restart.
→
3 · CoordinatorTerbangun, membaca pending/history, lalu memverifikasi.

Urutannya sengaja ketat: persist report sebelum callback. Jadi jika callback gagal, report tidak hilang. Jika callback terkirim dua kali, token kedua tidak boleh mengubah state. Dan acknowledgement hanya berarti “sudah diterima”, bukan “boleh merge atau cleanup”.

Lalu apa bedanya dengan /amux-tycho?

Karena Mas pembuat Tycho, framing yang paling tepat: /amux-tycho bukan orchestrator pengganti Tycho. Ia adalah adapter delivery di sisi Amp yang menerapkan ide serupa untuk hasil dari exact Tycho route, dengan boundary lebih ketat. Tycho tetap bebas mengorkestrasi provider di dalam domainnya, tetapi pada boundary ini Tycho hanya menjadi producer dengan authority report_only; Amp thread asli tetap coordinator, consumer, dan acknowledger.

Boundary Tycho (lokal · pinned): amux-tycho/SKILL.md:6–52 GitHub↗

Kenapa receipt bridge lebih kompleks? Bukan karena kami tidak mempercayai orchestration internal Tycho, tetapi karena boundary lintas sistem butuh bukti delivery sendiri. Kami mengikat origin Amp, exact Tycho route, dan digest task/artifact agar process exit atau prose dari log tidak disalahartikan sebagai report untuk request yang salah.

Seam yang ingin kami capai bersama Tycho

Idealnya, satu request Amp ke exact Tycho route mengembalikan tepat satu object terautentikasi pada turn yang sama: status, summary, findings, blockers, dan verification. Object itu harus correlated ke Amp thread/request dan task/artifact identity; tanpa fallback, transcript mining, side inbox, atau automatic retry. Kalau field run membuktikan seam ini, receipt + consume + acknowledge compatibility bridge tidak perlu dibuat untuk work baru.

Nuansa 2026: desainnya berhasil, produknya sedang cutover

Kami belajar bahwa mailbox + doorbell adalah pola yang benar. Tetapi native Amp kini sudah punya parent/child association, authenticated messaging, reply routing, dan waiting. Karena itu kami tidak ingin membuat database bayangan baru di Amux untuk setiap child baru.

KasusmuPilihan sekarang
Agent dan subagent sama-sama native AmpPakai native child creation + reply routing/waiting. Jangan onboard ke group/report Amux baru.
Sudah punya durable group/report Amux lamaDrain lewat report, pending/history, acknowledge, verifikasi, dan finish authorization yang ada.
Executor eksternal melalui Tycho/amux-tycho bisa dipakai secara explicit-only dan conditional; Tycho hanya mengirim typed report.
Orchestrator buatan sendiriAmbil kontraknya: durable report + cheap wake-up + idempotency + coordinator-owned verification. Tidak harus mengadopsi seluruh Amux.

Arah staged drain (lokal · pinned): ADR 0007:37–73 GitHub↗

Cold-recall defense, satu napas:
“Amux memisahkan durable truth dari wake-up: subagent persist report dulu, agent dibangunkan kemudian, lalu agent sendiri membaca, memverifikasi, dan acknowledge. Jadi callback boleh gagal tanpa kehilangan hasil.”

Jawaban yang bisa langsung dikirim ke temanmu

“Iya, Mas—secara pattern ini persis problem yang kami pecahkan di Amux. Daripada agent polling session subagent, subagent persist report saat ready/blocked, lalu mengirim wake-up kecil. Wake-up bukan datanya; kalau notifikasinya gagal, agent tetap bisa recover dari pending report. Agent kemudian baca, verify, dan acknowledge sendiri.

Di /amux-tycho, kami adaptasi pattern itu untuk output dari Tycho. Bukan mengganti orchestration Tycho: Tycho tetap mengatur agent/provider-nya, sedangkan boundary ke Amp hanya memberi Tycho authority report_only. Receipt mengikat Amp origin, exact Tycho route, dan task/artifact digest; hanya typed complete/blocked submit yang dianggap hasil—bukan process exit atau log.

Nuansanya, ini compatibility bridge yang masih experimental. Target akhirnya justru lebih simpel: exact Tycho route return satu structured result langsung ke invoking Amp turn, authenticated dan correlated. Kalau seam itu terbukti, side receipt/consume/ack tidak diperlukan untuk work baru. Untuk Amp-to-Amp sendiri kami sekarang pakai native parent/child reply routing, jadi group/report Amux lama sedang kami drain, bukan diperluas.”

Cek pemahaman

1. Callback gagal tepat setelah report berhasil disimpan. Apa sumber kebenarannya?
2. Tycho process exit tanpa structured submit berarti apa?
3. Untuk work Amp-to-Amp baru, jalur default saat ini apa?

Primary source

Baca ADR 0008: Retain the machine-local runner host and drain legacy coordination untuk arah saat ini: native Amp menangani koordinasi work baru, Amux tetap meluncurkan runner lokal, dan report lama hanya drain/compatibility. ADR 0007 tetap menjadi sejarah dan batas drain yang sebagian masih berlaku.
